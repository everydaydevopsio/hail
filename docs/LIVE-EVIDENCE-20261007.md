## Findings and non-passing setup attempts

Live `CreateLogGroup` with tags returned `AccessDeniedException` despite `logs:TagResource` on the unsuffixed group ARN. The provisioner policy now includes both ARN forms for the same run-owned group; no actions or other groups were added. Access Analyzer returned zero findings, and creation then succeeded. The regression assertion requires exactly those two ARN forms. AWS describes the different forms in its [LogGroup reference](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_LogGroup.html).

Initial reader role assumption failed during IAM propagation and succeeded on retry. The first `doctor` invocation used a config that attempted to assume the reader role again from an already-assumed reader; the direct-session config passed. The first 27 browser attempts stopped at the fixture's session-lifetime guard before sending mail; fresh sessions immediately followed by the suite passed. Separate transport launches also stopped before sending because of stale sessions or private harness setup errors (helper path and missing pinned STS test dependency); these were corrected before the passing run. The initial reader write canary used a non-regular input file and was excluded; its corrected request returned `AccessDenied`.

Detailed logs, manifests, saved plans/state, and the additional private transport/pipeline/indexer harnesses are retained under the private run directory for audit. They are not normal report attachments. Scope does not include another application's selectors or authorization contract, consumer inbox placement, Route53/manual provisioning, native SQS redrive tasks, or exhaustive real mutation denials for every IAM/DNS action.
